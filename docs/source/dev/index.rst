Contributing
============

The repository is a `pixi <https://pixi.sh>`_ workspace, and every check that CI runs is a pixi task you can run
locally with the same command.

Environment
-----------

.. code-block:: bash

    git clone https://github.com/jessegrabowski/gEconpy.git
    cd gEconpy
    pixi install
    pixi shell

``pixi install`` resolves the runtime, test and documentation dependencies from the committed ``pixi.lock`` and
installs gEconpy in editable mode. ``conda_envs/environment_dev.yml`` is the same environment exported for conda
users. It is generated by a pre-commit hook and is not edited by hand.

Tasks
-----

.. code-block:: bash

    pixi run test                    # the test suite; extra pytest arguments pass through
    pixi run test tests/solvers      # one directory
    pixi run lint                    # every pre-commit hook on every file
    pixi run -e docs docs-api        # regenerate the API reference pages
    pixi run -e docs docs-build      # build the documentation into docs/build/html

CI runs the test suite in subsets across Linux and Windows, runs the pre-commit hooks, regenerates the API pages
and fails if they differ from the committed ones, and builds the documentation. A pull request has to pass all of
them.

Code style
----------

Pre-commit with ruff is authoritative. Run ``pixi run lint`` before proposing a change. Docstrings are NumPy style
with human-readable types, and the documentation build treats every warning and every unresolved cross-reference
as an error, so a docstring that names a type or a function that does not exist fails the build.

Tests
-----

Tests live under ``tests/`` and mirror the package layout. Compile PyTensor functions once per test and sweep many
inputs through them, because repeated compilation dominates the run time. Prefer parametrization over conditionals
inside a test, and extend an existing test when the new coverage belongs with it.

Documentation
-------------

The API reference under ``docs/source/api/`` is generated by ``docs/generate_api.py`` from the import graph: one
page per module, listing the classes and functions the module defines, or exactly the names in its ``__all__`` when
it declares one. Do not edit those pages. A pre-commit hook regenerates them whenever a source file changes, and
CI fails when the committed pages are out of date.

The narrative pages under ``docs/source/user_guide/`` and ``docs/source/get_started/`` are written by hand. Code
samples on them are ``literalinclude`` directives that read from the shipped GCN files or from the test suite, so a
sample cannot drift from the code it shows.

Example notebooks live under ``docs/source/examples/`` and are executed before they are committed. The build does
not execute them. Every notebook tracked by git appears in the gallery automatically. To edit one, pair it with
jupytext (``jupytext --set-formats ipynb,_source//py:percent``), edit the script under ``_source/``, and sync, so
that the outputs survive the edit.
